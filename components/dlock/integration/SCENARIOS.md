# 分布式锁的生产故障场景

上线评估需要分别回答两个问题：后端是否还承认原租约，以及业务存储是否还接受旧持有者的写入。下面的测试用真实后端分别检查这两个结果。A 是原持有者，B 是接管者。

## Redis 主节点宕机与 Sentinel 切换

**拓扑。** Redis 7 一主一从，三个 Sentinel 监控同一个主节点，quorum 为 2。应用通过 go-redis Sentinel 客户端发现新主节点。测试先检查三个 Sentinel 都已发现副本和另外两个 Sentinel，并确认 quorum 可用。

**故障注入。** A 获取第一把锁，测试在副本上读到同一个 token 后才继续。随后暂停副本并断开已有复制连接，A 在旧主上成功获取第二把锁。两把锁的 TTL 都是 120 秒。测试终止旧主并恢复副本，等待 Sentinel 自动选主，核对三个 Sentinel 的发现结果和 Redis 的实际角色。

| 切换前的锁状态 | 切换后检查 | 上线判断 |
|---|---|---|
| 第一把锁已复制到被提升的副本 | A 成功续期，B 得到 `ErrLocked` | 这个用例验证了客户端能在切换后继续使用保留下来的租约。 |
| 第二把锁仅由旧主确认 | 新主没有该 key，B 在 A 原 TTL 到期前成功加锁。A 随后续期、解锁均得到 `ErrLockNotHeld`，B 仍可续期。 | 可以用于能容忍重叠执行的任务。要求单次副作用或有序写入时，需要在业务端去重或校验版本。 |

第一把锁是同一次切换中的对照组。应用收到 `Lock` 成功时通常不知道自己属于哪一组。测试主动制造复制缺口，用于验证可能发生的结果；一次切换耗时不能用作生产故障恢复承诺。[Redis Sentinel 的一致性说明](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

## etcd 原 leader 被隔离

**拓扑。** 三个 etcd 3.5 成员使用独立的 Raft 通信网络。每个成员还提供单独的客户端端点。测试通过三个成员的状态确认 leader，再由 A 在该 leader 上获取租约。

**故障注入。** 断开原 leader 的 Raft 网络，保留其客户端端点。两个多数派成员必须选出同一个新 leader。测试客户端分别固定到两侧，避免 SDK 改连健康成员掩盖少数派的行为。

| 阶段 | 通过条件 |
|---|---|
| 多数派完成选举，原租约还有效 | B 在多数派抢同名锁得到 `ErrLocked`。 |
| 少数派仍接受客户端连接 | A 续期失败；另一客户端在少数派申请全新锁名也失败。每次操作配置 1.5 秒预算，测试为调度抖动预留余量，超过 3 秒判失败。 |
| 原租约过期，网络仍分区 | B 在多数派成功接管并续期。 |
| 恢复 Raft 网络 | 原 leader 能线性一致地读到 B 的 token 和 lease ID。A 续期、解锁均返回 `ErrLockNotHeld`，B 仍可续期。 |

**上线判断。** 需要在单成员隔离时维持多数派协调的任务，可以采用三成员 etcd。业务必须接受少数派暂停工作。续期超时表示持有者无法确认租约，调用方应停止发起新的受保护操作。若外部资源可能收到暂停前已准备好的写入，还需在资源端处理旧请求。[etcd 集群故障模式](https://etcd.io/docs/v3.5/op-guide/failures/)

## 持锁进程暂停，接管后恢复

**拓扑。** Redis、MySQL、PostgreSQL、MongoDB、etcd、Consul 分别充当锁后端。业务数据统一写入真实 PostgreSQL 的独立测试行。测试在 Linux 或 macOS 启动独立的 Go 持锁进程，用操作系统信号暂停整个进程；数据库和接管者持续运行。

1. A 获取锁，读出业务行的版本 0，成功续期，随后向自己发送 `SIGSTOP`。父进程确认内核报告了子进程停止。此时 B 第一次抢锁必须得到 `ErrLocked`。
2. 保持 A 停止直至超过 TTL。B 成功接管后，在一次更新中写入两个对照字段并将版本推进到 1。测试等到这次写入成功才发出 `SIGCONT`。
3. A 在原来的指令位置继续。第一笔普通更新命中 1 行，把 B 的结果覆盖成 A 的旧值。第二笔更新带有 `WHERE id = ? AND version = 0`，命中 0 行，保留了 B 的结果。
4. A 再调用 `Refresh` 和 `Unlock`，两者都必须返回 `ErrLockNotHeld`。父进程独立读取最终字段和版本，并确认 B 还能续期和释放锁。

**上线判断。** 若重复执行和迟到的写入都能被业务接受，可以把锁用于减少重复工作。覆盖型写入需要在写入时校验预期版本，并处理影响行数为 0 的情况。扣款、发消息等副作用需要业务端按操作 ID 原子去重，或由下游提供相应保证。本测试验证了数据库条件更新；外部支付、消息系统及其幂等实现需要分别验证。

这里的版本来自业务行。dlock 的随机所有权 token 用于识别 Locker，无法给历次持有者排序。即使 A 刚刚续期成功，进程仍可在下一条业务写入之前暂停。

## 2026-11-27 实测记录

测试运行在 macOS 的 Docker Desktop，Go 测试启用 `-race`。下表是这次运行的观测值，用于说明故障发生的顺序。

| 故障 | 观测 |
|---|---|
| Redis Sentinel 切主 | 在三次独立建栈中，第二把锁均在 A 的 120 秒 TTL 内授给 B，分别耗时 4.434、4.343、4.388 秒。已复制的对照锁三次都保留。 |
| etcd 2+1 分区 | 客户端仍能查询少数派成员状态。最后一轮，少数派续期和新申请分别在 1.501、1.502 秒后返回截止时间错误。多数派在原租约有效时拒绝 B，过期后接受 B。 |
| 持锁进程暂停 | Redis、MySQL、PostgreSQL、MongoDB 和 etcd 使用 4 秒 TTL，A 实际停止约 4.11–4.42 秒；Consul 使用 10 秒 TTL，A 停止约 34.92 秒。六组的普通写都覆盖了新值，六组的条件写都保留了新值。 |

复测时应检查服务角色、锁所有权和最终业务行。Consul 的接管耗时包含 session 失效检测和 lock-delay；上述时间只代表本次配置与负载。

## 运行与适用范围

从 `components/dlock` 目录运行：

```sh
./integration/faults.sh  # Redis Sentinel 切主、etcd 三成员分区与恢复
./integration/run.sh     # 六种后端的租约契约、进程暂停与接管、MongoDB 专项测试
./test-unit.sh           # 单元测试的 99% 语句覆盖率门槛
```

每次运行使用独立的 Compose 项目、随机本机端口和临时存储，脚本退出时清理。生产故障用例会暂停或终止该项目的容器、断开并恢复成员网络。Go 集成测试启用 race 检测；日志记录第二次授锁距第一次确认的时间、少数派调用结果和持锁进程的实际暂停时长。

以上结论覆盖一台 Docker 主机上的指定故障。MySQL、PostgreSQL、MongoDB 和 Consul 在暂停场景中均为单节点；它们各自的主从切换、跨机房故障、备份恢复和长时间时钟漂移需要另外验证。Redis Cluster、多副本提升策略、多数派整体不可用以及端到端业务的恰好一次执行也不在本次结论范围内。
