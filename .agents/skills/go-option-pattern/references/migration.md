# 迁移说明：先保留语义，再替换结构

## 1. 盘点必须覆盖的范围

阅读目标包及其公开调用点，不只搜索 `type Option`。可使用仓库已有代码索引或搜索工具定位 `OptionFunc`、`WithXxx`、`DefaultOptions`、`NewOptions`、`Apply`、构造函数、测试、文档与生成代码。

记录以下表格，缺失项标记为未确认，不自行猜测：

| 项目 | 需要查明 |
| --- | --- |
| 类型 | 原 Option 是函数、泛型实例、接口，还是错误型函数 |
| 目标 | 作用于配置，还是直接修改已经创建的服务 |
| 默认值 | 所有来源、环境变量依赖、共享对象及初始化顺序 |
| 参数语义 | 合法零值、nil 含义、重复设置的覆盖/追加/合并规则 |
| 生命周期 | 创建、应用、校验、资源初始化、运行时更改及关闭 |
| 公开 API | 返回类型、函数签名、导出字段、实例字面量和序列化 |
| 数据所有权 | map/slice/嵌套指针/服务依赖/回调的归属 |
| 兼容性 | 是否已发布；已承诺行为；获准的变更范围 |

## 2. 从纯函数 Option 迁移

原接口：

```go
type Option func(*Options)
```

目标接口：

```go
type Option interface {
    apply(*Options)
}

type OptionFunc func(*Options)

func (f OptionFunc) apply(o *Options) {
    f(o)
}
```

典型改法：

```go
// 原来：
func WithRetries(n int) Option {
    return func(o *Options) { o.retries = n }
}

// 迁移后：
func WithRetries(n int) Option {
    return OptionFunc(func(o *Options) { o.retries = n })
}
```

包内原 `opt(o)` 改为目标的 `opt.apply(o)`，但不要重复散布应用循环：构造配置统一通过 `NewOptions`/`Apply`。

### 公开 API 的变化

- 直接传入 `func(*Options)` 的地方需要 `OptionFunc(...)` 适配。
- 原 `Option(fn)` 的函数类型转换需要改为 `OptionFunc(fn)`；旧的可调用性不再保留。
- 外部 `opt(o)` 不能继续调用；需要应用单个选项时可使用 `o.Apply(opt)`，不要导出 `apply`。
- `[]OptionFunc` 不能直接作为 `[]Option` 展开；按现有需要构造 `[]Option`，不新增 `...any`。
- 依赖具体返回类型的函数变量、反射、生成代码与下游测试也需要审计。
- 声明导出适配器之后，不能再把 `Option` 描述为完全不允许外部扩展。

从函数改成接口是公开类型变更，即使 `New(WithTimeout(...))` 这一常见调用不变，也不能据此宣称无破坏性。语言规则与模块兼容性依据见 `design-notes.md`。

## 3. 从泛型 Option 迁移

只移除目标配置机制对公共泛型 Option 工具的依赖。每个业务包自行定义具体的 `Option`、`OptionFunc` 和 `Options`，无需新的公共抽象包。

替换类型别名与泛型 `Apply` 调用后，再确认旧工具是否仍被其它地方引用。只在确认无引用且在任务范围内时清理依赖，不擅自删除整个公共模块或运行不必要的依赖升级。

如果配置类型本身是公开泛型类型，不要强制把整个库去泛型化。本 Skill 的具体 `*Options` 目标形态可能不直接适用，应说明冲突并保留非目标业务设计。

## 4. 从既有接口迁移

已有 `Option` 接口、私有 apply、函数适配器时，优先复用。只统一当前缺失的职责或命名，不为了“与模板一致”重写稳定的所有实现。

若目标不是 `*Options` 而是运行中的 `*Client`，先确认该 Option 是否承担资源配置或热更新。不能把一个新结构体包在外面就认为构造语义等价。

若适配器原本私有，只有目标确实要求开放组合能力时才导出为 `OptionFunc`；本 Skill 的默认目标是导出，但实际变更应在说明中列出。不要删除原有公开符号来追求名称整齐。

## 5. 错误型选项的处理

本 Skill 不新增第二套 `OptionErr`。但“不新增”不等于可以无损删除原库已有的错误契约。

| 原行为 | 迁移判断 |
| --- | --- |
| 单字段纯检查 | 可考虑最终统一检查；先确认错误时机与顺序改变是否获准 |
| 跨字段检查 | 最终状态检查通常符合新约定；锁定原需求，不照搬示例规则 |
| 字符串解析/格式编译 | 保留解析错误与调用链；是否延后必须有明确决策 |
| 网络、文件、资源创建 | 分离配置组装与资源初始化，保留失败与清理行为 |
| 遇错立即停止 | 不能用无错误 Apply 自动替代，改变的是可观察行为 |

禁止采用 `_=oldApply(...)`、忽略错误、把所有错误 panic、返回带错误但可运行的对象，或在 `Options` 中塞一个隐藏 `err` 字段伪装完成迁移。

已经返回错误的构造函数应保持错误包装与身份语义。没有错误返回值的公开构造函数，新增返回值也是破坏性变更。

## 6. 字段私有化与解码边界

需要审计：`Options{Timeout: ...}`、直接读写、JSON/YAML/mapstructure/flag 绑定、反射与生成代码。私有字段不能因保留 struct tag 就继续按原方式解码。

优先按已有层次区分“外部输入结构”和“内部构造配置”。只有确有输入解码需求时才考虑现有 DTO、显式转换或专门边界方法，不为本 Skill 平白引入一套 DTO 框架。

未授权改变公开字段或已发布解码格式时，不能静默私有化。完成兼容部分，在交付中明确哪些字段/入口尚未迁移及原因。

## 7. 保留每个选项的原始语义

原追加型 `WithHooks(a)`、`WithHooks(b)` 应继续保留 a 和 b，不统一改成后者覆盖。原合并型 map 应保留键冲突规则。是否支持重复应用、nil 清空或空集合，与本次接口选择无关。

不要对选项排序、去重或并行应用。即使标量设置可幂等，也不能推导所有选项可幂等。

默认独立、输入复制和运行时只读应分别落实。若原有可观察行为允许调用方后续修改输入生效，改成快照也属于语义变化，要先记录再按授权处理。

## 8. nil 与历史契约冲突

目标 `Apply` 不判空、不跳过、不 recover。无效输入不属于该新 API 支持的使用方式。

如果原库明确支持 nil Option、nil receiver，或已有用户依赖静默跳过，则这是迁移冲突，而不是删掉分支就算修复。应遵循获准的破坏性变更/版本策略；没有授权时，不强推新行为。不要通过把防御搬到适配器里来伪装遵循目标设计。

## 9. 发布前检查与交付

按包列出新增、移除、类型变化及签名变化；更新示例；保留原仓库 changelog 和发布策略。版本决策由维护者现有规则决定，不自行发布版本。

存在未确认的外部消费者时，只能说明“已更新仓库可见调用点”，不能说明“所有调用方兼容”。已授权内部整体升级时可以直接调整受控调用点，但仍记录破坏点。

交付示例：

```text
范围：pkg/client 与仓库内相关调用方。
保持：超时默认值、0 重试、追加 Hooks、原错误身份。
变化：Option 从函数改接口；自定义函数通过 OptionFunc 适配。
检查：逐项写真实命令、工作目录、结果和限制。
未覆盖：仓库外消费者、未运行的 build tags 或平台。
```
